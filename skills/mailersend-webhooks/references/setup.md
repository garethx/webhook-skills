# Setting Up MailerSend Webhooks

## Prerequisites

- A MailerSend account with a **verified sending domain** — webhooks are created
  per domain, so you can't add one until a domain exists
- Your application's webhook endpoint URL, reachable over HTTPS and returning a
  **2xx within 3 seconds**
- For the API route: a MailerSend API token with webhook management permissions

## Create a Webhook in the Dashboard

1. Log in to MailerSend.
2. Go to **Email → Domains**.
3. Click **Manage** on the domain you want events for.
4. Scroll to **Webhooks** and click **Add webhook**.
5. Enter a **name** (max 50 characters) and your **endpoint URL** (max 191
   characters).
6. Select the **webhook version** — MailerSend recommends **V2**. (The docs list
   `1 Legacy, 2 Recommended` but do not document what differs between them; use
   V2 for new integrations.)
7. Select the events to subscribe to, or choose **receive all events**.
8. Click **Save webhook**.

**Your endpoint must already be live and returning 2xx before you click Save.**
See "The URL validation request" below — this is the single most common reason a
MailerSend webhook won't save.

## Get Your Signing Secret

After the webhook saves, open it from the webhook management page (Domains →
Manage → Webhooks → your webhook). The **signing secret** is shown there — copy
it into your app as `MAILERSEND_WEBHOOK_SECRET`.

```bash
MAILERSEND_WEBHOOK_SECRET=your_webhook_signing_secret
```

Key facts:

- The secret is **generated by MailerSend** when the webhook is created. You
  don't choose it.
- It is **per-webhook**. Two webhooks on the same domain have different secrets.
- It is **not** your MailerSend API token. Signing with the API token fails every
  verification.

## The URL Validation Request (`webhook.test`)

When you create or update a webhook, MailerSend immediately POSTs a validation
request to the URL. **If it doesn't get a 2xx back, the webhook is not saved.**

```json
{
  "type": "webhook.test",
  "message": "This is a ping test message",
  "created_at": "2026-03-27T07:24:20.577080Z"
}
```

Two things about it differ from every real event:

1. **The envelope.** It has `message`, not `data`. Handlers that touch
   `payload.data` before switching on `type` throw a 500 on the ping.
2. **The secret.** It is signed with the fixed, publicly documented secret
   `test_Am3L1GuOIc4blLUuHqAPxxwkZaJyEk8G` — **not** your webhook's signing
   secret. A handler that only accepts the real secret rejects the ping, and the
   webhook never saves.

Your handler must accept **either** secret, and — because the test secret is
public and therefore forgeable by anyone — must only allow a test-secret
signature to authorise a `webhook.test` payload. Never let a `webhook.test`
request gate privileged work. The examples in this skill do exactly this.

## Create a Webhook via the API

`POST https://api.mailersend.com/v1/webhooks/`

```bash
curl -X POST https://api.mailersend.com/v1/webhooks/ \
  -H "Authorization: Bearer $MAILERSEND_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/webhooks/mailersend",
    "name": "Order emails",
    "events": ["activity.delivered", "activity.hard_bounced", "activity.spam_complaint"],
    "domain_id": "yv69oxl5kl785kw2",
    "version": 2
  }'
```

| Parameter | Required | Notes |
|-----------|----------|-------|
| `url` | Yes | Max 191 chars |
| `name` | Yes | Max 50 chars |
| `events` | Yes | Array of event names — see [overview.md](overview.md) |
| `domain_id` | Yes | The sending domain |
| `enabled` | No | Boolean |
| `editable` | No | Boolean |
| `version` | No | `1` (legacy) or `2` (recommended) |

The response includes the generated `signing_secret`.

Other endpoints:

| Method | Endpoint | Purpose |
|--------|----------|---------|
| `GET` | `/v1/webhooks?domain_id={id}` | List webhooks (`domain_id` is required) |
| `GET` | `/v1/webhooks/{webhook_id}` | Retrieve one webhook |
| `PUT` | `/v1/webhooks/{webhook_id}` | Update (re-fires the validation request) |
| `DELETE` | `/v1/webhooks/{webhook_id}` | Delete |

## SMS Webhooks

SMS webhooks are configured separately under **SMS → Webhooks**, with their own
endpoints:

| Method | Endpoint |
|--------|----------|
| `GET` | `/v1/sms-webhooks` |
| `GET` | `/v1/sms-webhooks/{sms_webhook_id}` |
| `POST` | `/v1/sms-webhooks/` |
| `PUT` | `/v1/sms-webhooks/{sms_webhook_id}` |
| `DELETE` | `/v1/sms-webhooks/{sms_webhook_id}` |

The security model is identical — same `Signature` header, same HMAC-SHA256 hex
over the raw body, same per-webhook signing secret, same fixed test secret — so
the same verifier works. Events are `sms.sent`, `sms.delivered`, `sms.failed`.

## Testing

**From the dashboard:** open the webhook, and under **Events** click **Test
webhook**, then pick a test event from the dropdown.

**Locally, with a real tunnel:**

```bash
npx hookdeck-cli listen 3000 mailersend --path /webhooks/mailersend
```

Use `8000` instead of `3000` for the FastAPI example. Paste the printed URL as
the webhook URL. The `webhook.test` ping arrives the instant you save, which is
a free end-to-end check of your ping handling. No Hookdeck account is required —
the CLI creates a guest account on first run and gives you a web UI for
inspecting requests.

## Pausing and Re-enabling

- Pause manually: **Edit** the webhook and flip the **Status** toggle from
  Enabled to Disabled.
- MailerSend also pauses a webhook **automatically** after an extended run of
  failures (retries continue with exponential backoff for about 3 days first).
  Re-enable it from the dashboard.

## Delivery Expectations

- A failed attempt is any non-2xx response, or no response within **3 seconds**.
- Retries use exponential backoff for **~3 days**.
- **4xx other than 429, and DNS resolution failures, are never retried.**
- Acknowledge with 2xx immediately and do the work in a background job.

## Using the Hookdeck MailerSend Source

Hookdeck ships a first-class `MAILERSEND` source type. It verifies the same way
this skill does — HMAC-SHA256, hex, read from the `Signature` header — and the
dashboard field it asks for, **Webhook Signing Secret**, is the per-webhook
signing secret, not your API token.

The public test secret creates one ordering trap. MailerSend sends the
`webhook.test` ping on **create and update**, signed with the fixed public
secret rather than your signing secret. A source that is already verifying with
your real signing secret rejects that ping — and MailerSend refuses to save a
webhook whose URL did not answer 2xx. So:

1. Create the Hookdeck source with verification **not yet configured**.
2. Point a new MailerSend webhook at the source URL and save. The ping gets its
   2xx, the webhook saves, and the signing secret is generated.
3. Copy that signing secret into the source's verification config.

Real events then verify normally. Note the consequence for later edits: because
the re-validation ping fires on **update** too, changing the webhook's URL while
the source is verifying will fail to save. Clear the source's verification for
the duration of the edit, then restore it.

## Production: Put a Gateway in Front

MailerSend gives you ~3 days of retries and then pauses the webhook. If your
handler is down longer than that, or a deploy drops events, the events are gone.
[Hookdeck Event Gateway](https://github.com/hookdeck/webhook-skills/tree/main/skills/hookdeck-event-gateway)
gives you durable ingestion, independent retries, replay and delivery
observability in front of your handler.
