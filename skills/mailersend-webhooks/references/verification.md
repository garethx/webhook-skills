# How to Verify MailerSend Webhook Signatures

## How It Works

From the [MailerSend docs](https://developers.mailersend.com/api/v1/account/webhooks.html#security):

> Webhook requests made by MailerSend include a `Signature` header. It contains a
> string generated by hashing the data sent to your webhook endpoint with an
> individual Signing Secret. A signing secret is a random string that is
> generated when you create a webhook.

| Property | Value |
|----------|-------|
| Header | `Signature` — exactly that. No `X-` prefix, no vendor prefix. |
| Algorithm | HMAC-SHA256 |
| Encoding | **lowercase hex** (the docs use `.digest('hex')` / `hex.EncodeToString`) — **not** base64 |
| Signed content | The **raw request body**, exactly as received, and nothing else |
| Key | The per-webhook **Signing Secret**, used as the raw UTF-8 key string |
| Comparison | Constant time |

**There is no timestamp, no nonce, no version prefix, no `t=…,v1=…` element
list, and no field concatenation.** The header value is the bare hex digest:

```
Signature: 3f9a2c1b...64 lowercase hex characters...
```

This is **not** Standard Webhooks — there are no `webhook-id`,
`webhook-timestamp` or `webhook-signature` headers.

## Implementation

### Node.js / JavaScript

```javascript
const crypto = require('crypto');

function verifySignature(rawBody, signature, secret) {
  if (!signature || !secret) return false;
  const expected = crypto.createHmac('sha256', secret).update(rawBody).digest('hex');
  const a = Buffer.from(String(signature).trim().toLowerCase(), 'utf8');
  const b = Buffer.from(expected, 'utf8');
  // timingSafeEqual THROWS on a length mismatch — check the length first.
  // The digest length is public, so leaking it costs nothing.
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```

`rawBody` must be a `Buffer` or the exact body string. Passing a re-serialised
object breaks verification for any payload MailerSend does not send in byte-identical form.

### Python

```python
import hashlib
import hmac

def verify_signature(raw_body: bytes, signature: str, secret: str) -> bool:
    if not signature or not secret:
        return False
    expected = hmac.new(secret.encode("utf-8"), raw_body, hashlib.sha256).hexdigest()
    # compare_digest raises TypeError on non-ASCII str, so compare bytes
    return hmac.compare_digest(signature.strip().lower().encode("ascii", "ignore"), expected.encode("ascii"))
```

### The official SDKs

**Node (`mailersend`)** ships a `MailerSendUtils.verifyWebHook(rawBody, signature, signingSecret)`
helper, but as of `mailersend@3.2.0`:

- It is **not exported from the package entry point**. `require('mailersend').MailerSendUtils`
  is `undefined`; you'd need the undocumented deep import
  `require('mailersend/lib/services/mailersend.utils')`.
- It calls `crypto.timingSafeEqual` **without a length guard**, so a malformed or
  truncated `Signature` header throws `RangeError: Input buffers must have the
  same byte length` instead of returning `false` — an unhandled 500 on
  attacker-controlled input.
- Its README's usage snippet reads the signature from
  `request.headers['x-mailersend-signature']`. **No such header is sent.** The
  API docs' Security section and all six of its language samples use `Signature`
  (the Go sample calls `r.Header.Get("Signature")` outright), and that is the
  header on real deliveries. Copy the SDK snippet verbatim and you pass
  `undefined` as the signature, which the helper rejects with
  `Error: No signature provided` — a 500 on every delivery.

**Python (`mailersend`)** ships no webhook verification helper at all. As of
`mailersend==2.0.3` the only signing-related thing in the package is a
`signing_secret` field on the SMS-webhook model.

Verify manually, as the official docs' own Node, Go and PHP samples do. That is
what the examples in this skill do.

## Handling the `webhook.test` Ping

MailerSend signs its URL-validation ping with a **fixed, publicly documented**
secret rather than your webhook's signing secret:

```
test_Am3L1GuOIc4blLUuHqAPxxwkZaJyEk8G
```

If your handler only checks the real secret, the ping is rejected, MailerSend
doesn't get a 2xx, and **the webhook is never saved**. So you must accept both.

But because that secret is public, **anyone can forge a signature that verifies
against it**. Accepting it unconditionally would mean anyone on the internet can
deliver a "verified" event to your handler. The safe pattern:

```javascript
const MAILERSEND_TEST_SECRET = 'test_Am3L1GuOIc4blLUuHqAPxxwkZaJyEk8G';

const signedByYou = verifySignature(rawBody, signature, process.env.MAILERSEND_WEBHOOK_SECRET);
const signedByPing = !signedByYou && verifySignature(rawBody, signature, MAILERSEND_TEST_SECRET);

if (!signedByYou && !signedByPing) return res.status(401).send('Invalid signature');

const event = JSON.parse(rawBody.toString('utf8'));

if (event.type === 'webhook.test') {
  // Must be 2xx or the webhook won't save. Do NOT do privileged work here.
  return res.status(200).json({ received: true });
}

if (signedByPing) {
  // The public test secret can only ever authorise the ping.
  return res.status(401).send('Invalid signature');
}

// ...only now is this a genuine, authenticated MailerSend event
```

## Common Gotchas

**Use the raw body, always.** The digest covers the exact bytes received.
Whitespace, key order and Unicode escaping all change the bytes. Configure your
framework to hand you the unparsed body:

| Framework | How |
|-----------|-----|
| Express | `express.raw({ type: '*/*' })` — `req.body` is a `Buffer`. Register it on the webhook route **before** any global `express.json()` |
| Next.js App Router | `const rawBody = await req.text()` in the route handler |
| FastAPI | `raw_body = await request.body()` — take `Request`, not a Pydantic model |

`express.raw({ type: 'application/json' })` also works, but silently leaves
`req.body` as an empty `{}` if MailerSend ever sends a different content type.
`'*/*'` avoids that failure mode.

**The key is the secret string itself.** Don't hex-decode, base64-decode or
otherwise transform it before using it as the HMAC key.

**Don't use your API token.** The signing secret is per-webhook, shown on the
webhook management page. The API token (`mlsn.…`) is a different credential.

**Header lookup is case-insensitive, but the name isn't `X-Signature`.** Node's
`req.header('Signature')` and FastAPI's `request.headers.get("signature")` both
work; `X-Signature` and `X-MailerSend-Signature` do not exist.

**Guard the length before `timingSafeEqual`.** Node's `crypto.timingSafeEqual`
and Python's `hmac.compare_digest` differ here: `compare_digest` returns `False`
on unequal lengths, `timingSafeEqual` **throws**. An attacker sending
`Signature: x` would turn an unguarded comparison into a 500.

**`Buffer.from(sig, 'hex')` silently truncates.** `Buffer.from('zz', 'hex')` is
an empty buffer, so decoding both sides from hex before comparing can make
garbage input compare equal-length. Compare the hex **strings** (as UTF-8 bytes)
instead, as above.

**There's no timestamp, so you can't do replay protection at the transport
layer.** Dedupe on `data.id` in your application instead. See
[idempotency](https://github.com/hookdeck/webhook-skills/blob/main/skills/webhook-handler-patterns/references/idempotency.md).

**`data.meta` is `[]` when empty.** Not `{}`, not `null` — an empty JSON array.
Typed deserialisation into a map/dict fails. Normalise:
`Array.isArray(data.meta) ? {} : data.meta`.

**`created_at` has two formats.** `2025-08-05T21:23:54.000000Z` for activity and
inbound events; `2025-08-05 22:27:14` (space-separated, no timezone) for
`sender_identity.verified` and `maintenance.*`.

**A rejected signature is not retried.** MailerSend treats 4xx other than 429 as
unrecoverable, so a broken verifier means every event during the outage is lost —
not queued. Fix verification before going live, and consider a gateway in front.

## Debugging Verification Failures

| Symptom | Likely cause |
|---------|--------------|
| Every request fails, including the ping | Wrong secret (API token instead of signing secret), or body is being parsed before verification |
| The ping fails but you never see real events | You only accept the real signing secret — the webhook never saved. Accept `test_Am3L1GuOIc4blLUuHqAPxxwkZaJyEk8G` for `webhook.test` |
| Works locally, fails in production | A proxy, body-parser or logging middleware is re-serialising the body. Verify before anything touches it |
| Intermittent failures on some payloads only | Non-ASCII content — you're re-serialising and your JSON encoder escapes Unicode differently from MailerSend's |
| `RangeError: Input buffers must have the same byte length` | `timingSafeEqual` without a length guard |
| `TypeError: unsupported operand` / non-ASCII in `compare_digest` | Comparing `str` instead of `bytes` in Python |
| Signature is 64 chars but never matches | You base64-encoded instead of hex, or you're signing `timestamp.body` — MailerSend signs the body alone |

To isolate the problem, log the computed digest next to the received header for a
single request in a non-production environment:

```javascript
console.log({
  received: req.header('Signature'),
  computed: crypto.createHmac('sha256', secret).update(req.body).digest('hex'),
  bodyLength: req.body.length,
  bodyIsBuffer: Buffer.isBuffer(req.body),  // must be true
});
```

If `bodyIsBuffer` is `false`, that's your bug — the body was parsed before you
got to it. Never leave that log in production; it discloses a valid signature.
